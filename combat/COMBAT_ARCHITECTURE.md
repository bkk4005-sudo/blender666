# Combat architecture

Current pacing: `config/action_pacing.json` is the authored schedule for both Blender pose retiming and generated `CombatPacing.luau`. CombatConfig merges that schedule with damage, stamina and hit-profile settings. ActionTimeline and client duration/combination gates read the resulting config. Rolls have an explicit movement window followed by stationary recovery; expanding duration does not proportionally expand invulnerability. Client lock-on attack turn limits use the same per-action setting as server blade orientation. See COMBAT_PACING.md.

Roll presentation is now exclusive: Action4 source/registry/track priority, local state guard established on the first predicted input, no competing attack/parry predictions, and immediate suppression of foreign action tracks during the roll. Server-authorized reactions and death remain able to interrupt. Roll-facing AlignOrientation is disabled while rolling, preserving the server motion direction. Combo R1 only submits an input; the server's Started event switches clips at chainAt. Sequence-specific Rejected responses roll back rejected predictions. Balance windows and server i-frames remain independent of animation markers.

## Avatar visuals and controls (prototype 2.4)

WeaponVisual equips the server-owned unscaled sword template after appearance loading and retries on CharacterAppearanceLoaded. One Motor6D holds the rigid mesh; no visual part supplies authoritative damage. BladeClearance preserves limb lengths/grip while rotating the shoulder away from body-box intersections. AvatarWeaponClearance renders this overlay on each observed player after Animator evaluation, restores it before the next evaluation and uses a fast safe-correction path. AvatarGroundClearance changes only the visual root joint during action states.

The weapon's scaled RightGrip frame is attached to the avatar's native RightGripAttachment. `WeaponVisualConfig.forCharacter` resolves that palm frame for equipment, preview bakes, blade clearance and floor clearance. The measured standard R15 palm reference is used in Blender and as a fallback. Canonical export separately calibrates anatomical arm axes, so the donor's splayed mesh rest pose is not added as an extra bend on a standard avatar.

InputBindings defines the seven semantic actions, defaults and validation. CombatSettings provides the menu and applies bindings immediately; CombatSettings.server validates/coalesces persistence independently of combat. Preference data cannot change attack kind validation, damage, stamina or i-frames. Held block/sprint release on menu, chat, focus loss, End or Cancel. Block stops sprint drain; guard break stops movement and broadcasts its real reaction clip.

R15PreviewRetarget exposes an avatar bake shared by Studio preview playback and server blade-path compilation. It resolves actual joint frames, proportions, native palm grip, body clearance and HipHeight translation-scale compensation. Its `forCharacter` preview entry point remains Studio-only. Published animation playback remains gated by absent AnimationIds.

`src/shared/CombatConfig.luau` owns the prototype balance numbers. `ActionTimeline.luau` derives server phases and windows from the same config. `AnimationRegistry.luau` maps semantic names to per-rig animation assets and reserves profile registration for future custom rigs. Animation IDs do not drive damage or stamina.

`src/server/CombatService.luau` owns one profile per player: character generation, sequence number, rate counter, state, stamina, active action, hit set, compiled blade paths and temporary motion actuator. It rejects nonfinite request values, repeated/out-of-order sequences, excessive action requests and impossible state transitions. Held block/sprint releases remain available after a request burst. A combo is queued only when the second attack's stamina cost can be paid, then charged when that action starts. It applies damage once per humanoid per action, checks defender roll windows, facing, parry and block, and cleans up on death/respawn. Invulnerability does not consume the attack's hit entitlement, so a target still overlapping the later active window can be struck. Static models with `CombatDummy=true` receive damage but keep at least 1 HP and heal after a delay.

`src/client/CombatClient.client.luau` sends intent only. It starts local animation prediction, listens for server starts, caches tracks and uses real marker signals only for future VFX/SFX. Lock-on camera and facing are local; lock is released if the target dies, exits range, is removed, or stays occluded for 0.75 s. The server decides damage from its action schedule and observed physical root positions. Client animation markers, joint Transforms, AnimationTrack time, hit reports and claimed damage are not authoritative inputs.

## Server blade contact

`src/server/BladeTrajectory.luau` compiles the three attack paths from our real R15 KeyframeSequences. Each source is baked for the completed avatar appearance; forward kinematics use that rig's Motor6D or AnimationConstraint attachment frames and native palm grip. LowerTorso translation is rescaled consistently with the preview Animator compensation. The resulting samples contain the blade base and tip relative to HumanoidRootPart, with linear interpolation between authored samples.

After CharacterAppearanceLoaded, `prepareBladePaths` rebuilds all three attack caches in a task that yields during avatar baking. `CombatHitReady` stays false until all paths are available. Player sword attacks are rejected before readiness without spending stamina, so first contact does not synchronously compile a full avatar animation. Character generation checks prevent an old preparation task from installing paths after death/respawn; appearance reload starts a new generation. Unsupported or missing joints fail closed and expose `CombatHitRigError`.

The service updates at 30 Hz and clips every elapsed sweep interval to the attack's server-owned active window. It samples that interval at approximately 60 Hz, with a bounded subdivision count, including the final segment when an update crosses activeEnd. Once activeEnd is processed, later recovery updates cannot repeat its end pose. The pending first-attack interval is swept before a queued combo changes to SwordR1_2; if that interval is parried, its Stagger state and cleared combo remain in force. Samples combine the authored path with interpolated server root position and the action's limited facing direction. A root displacement over 2 studs between updates disables that positional bridge; this guards against a long damage ribbon and is not movement anti-cheat or lag compensation.

The broad phase finds nearby parts around the blade segment and its preceding sample. The narrow phase tests current, previous, middle and connecting segments against each body's oriented bounding box, expanded by 0.18 studs on each local axis. HumanoidRootPart, accessories and weapon models are excluded as hurtboxes. `BladeTrajectory.query` returns candidate records `{part, origin, contact}` for each Humanoid. `contact` is the segment's entry point into the expanded box, and `origin` is the corresponding blade-base position. A swept tip contact keeps the preceding blade base as its visibility origin. Multiple intersected parts and segments remain candidates.

Server raycasts with RespectCanCollide check root-to-candidate-origin and candidate-origin-to-contact obstruction. Visibility ends at the actual sampled intersection, so a raised torso centre cannot let a low blade contact pass through cover. An unobstructed candidate can receive damage even when another intersected part is covered. Range and one-hit-per-action checks still apply; a successful parry immediately stops the old attack's remaining sweep, combo transition and phase update.

This is an approximation of body and blade geometry. The 0.18-stud expansion is a project hit tolerance, not a measured DS3 value or exact mesh collision. Clothing, hair and accessories do not enlarge hurtboxes; cosmetic clearance and Animator blending can also differ from sampled poses. Controlled Studio contact tests and isolated request/defense/lifecycle suites are recorded in TEST_REPORT.md. Two-player latency, observer alignment, rewind and final competitive balance remain unverified. Published animation access and these multiplayer checks are required before any release claim.

The current package contains nine shared modules, five server scripts/modules, three client LocalScripts and twelve animation sources. `tools/import_studio.luau`, `tools/update_studio_animations.luau` and the generated XML bundle include BladeTrajectory and the shared retarget dependencies. Map geometry is outside this package.

The default Roblox `Humanoid` remains the movement primitive. `WalkSpeed` limits action movement; a plane-mode `LinearVelocity` applies authored roll and sword-attack displacement without constraining vertical velocity. The roll and attack advance use bounded rise/plateau/fall speed curves. During attacks, server sweep orientation follows the server-observed root at no more than the configured turn rate. A client roll vector must have near-unit horizontal magnitude and agree with its chosen relative animation direction. Blender root transforms are visual and do not move the HumanoidRootPart. The current system does not offer custom acceleration or lock-on locomotion animations, and client lock-on input requires integration review alongside the project's PlayerModule and existing controls.
